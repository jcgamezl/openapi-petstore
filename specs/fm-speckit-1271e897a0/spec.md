## 1. Project Overview

`openapi-petstore` is a Spring Boot 2 REST API that implements the canonical OpenAPI 3 Petstore sample specification. It demonstrates an **API-First / Contract-Driven Development** pattern: the `openapi.yaml` file is the authoritative source of truth, and all three resource domains — **Pet**, **Store**, and **User** — are implemented via generated delegate interfaces backed by lightweight in-memory (`HashMap`) repositories. The application is secured with OAuth2 (`spring-security-oauth2-autoconfigure`) and is containerised via a `Dockerfile`.

**US-PET-01 — Add a new pet**
> As an authenticated API consumer, I can submit a new pet record so that it becomes discoverable in the store's catalogue.

- **Endpoint:** `POST /pet`
- **Auth Required:** Yes (OAuth2 scope: `write:pets`)
- **Request Body:** Pet object (name, photoUrls required; id, category, tags, status optional)
- **Success Response:** `200 OK` with the created Pet object
- **Failure Response:** `405 Method Not Allowed` when input data is invalid
- **Implementation:** `PetApiDelegateImpl.java` → `PetRepository.java` (save operation)

---

**US-PET-02 — Update an existing pet**
> As an authenticated API consumer, I can update the details of an existing pet record so that the catalogue stays accurate.

- **Endpoint:** `PUT /pet`
- **Auth Required:** Yes (OAuth2 scope: `write:pets`)
- **Request Body:** Complete Pet object including `id`
- **Success Response:** `200 OK` with the updated Pet object
- **Failure Responses:** `400 Bad Request` (invalid ID supplied), `404 Not Found` (pet not found), `405 Method Not Allowed` (validation exception)
- **Implementation:** `PetApiDelegateImpl.java` → `PetRepository.java` (update operation)

## 5. Functional Requirements

### FR-1 — Contract Fidelity
> Source: `src/main/resources/openapi.yaml` (820 lines) + Constitution Principle 1

- **FR-1.1** Every endpoint, request body shape, query parameter, path parameter, and response schema MUST match the definitions in `openapi.yaml` exactly.
- **FR-1.2** The `openapi.yaml` file MUST be served at runtime so that Swagger UI renders live documentation (via `OpenAPIConfiguration.java`).
- **FR-1.3** Responses MUST include the correct HTTP status codes as defined in `openapi.yaml` for both success and error paths.

### FR-2 — Pet Lifecycle
> Source: `PetApiDelegateImpl.java`, `PetRepository.java`

- **FR-2.1** Pets MUST be creatable via `POST /pet` with at minimum `name` and `photoUrls`.
- **FR-2.2** Pets MUST be retrievable by ID (`GET /pet/{petId}`), by status (`GET /pet/findByStatus`), and by tags (`GET /pet/findByTags`).
- **FR-2.3** Pet updates MUST support both full replacement via `PUT /pet` and partial form-data update via `POST /pet/{petId}`.
- **FR-2.4** File uploads for pet photos MUST return an `ApiResponse` confirming upload success or failure (`POST /pet/{petId}/uploadFile`).
- **FR-2.5** Pet deletion via `DELETE /pet/{petId}` MUST require OAuth2 `write:pets` scope; absent pets MUST return `404`.

### FR-3 — Order Lifecycle
> Source: `StoreApiDelegateImpl.java`, `OrderRepository.java`

- **FR-3.1** Orders MUST be placeable without authentication (`POST /store/order`).
- **FR-3.2** The inventory endpoint (`GET /store/inventory`) MUST aggregate pet counts grouped by status and return a `Map<String, Integer>`.
- **FR-3.3** Order IDs submitted to `GET /store/order/{orderId}` and `DELETE /store/order/{orderId}` MUST be validated to be in the range 1–10; values outside this range MUST return `400 Bad Request`.
- **FR-3.4** Order `shipDate` MUST be serialized in RFC 3339 format via `RFC3339DateFormat.java`.

### FR-4 — User Lifecycle
> Source: `UserApiDelegateImpl.java`, `UserRepository.java`

- **FR-4.1** Users MUST be creatable individually (`POST /user`) or in bulk (`POST /user/createWithArray`, `POST /user/createWithList`).
- **FR-4.2** Login (`GET /user/login`) MUST return a session token string and set `X-Rate-Limit` and `X-Expires-After` response headers.
- **FR-4.3** Logout (`GET /user/logout`) MUST invalidate the current session.
- **FR-4.4** User lookup, update, and deletion MUST key on the `username` string field, not numeric ID.
- **FR-4.5** An attempt to look up or delete a non-existent username MUST return `404 Not Found`.

### FR-5 — Security
> Source: `SecurityConfiguration.java`, `ResourceServerConfiguration.java`, `AuthorizationServerConfiguration.java`

- **FR-5.1** All `/pet/**` write operations (`POST`, `PUT`, `DELETE`) MUST require a valid OAuth2 token with `write:pets` scope.
- **FR-5.2** All `/pet/**` read operations (`GET`) MUST require a valid OAuth2 token with `read:pets` scope.
- **FR-5.3** `/store/inventory` MUST be protected (OAuth2 or API key header).
- **FR-5.4** `/store/order/**` endpoints MUST be publicly accessible without authentication (per `openapi.yaml` security definitions).
- **FR-5.5** All `/user/**` mutation endpoints MUST be restricted to admin-level access.
- **FR-5.6** Unauthorized requests MUST receive `401 Unauthorized`; forbidden requests (insufficient scope) MUST receive `403 Forbidden`.

### FR-6 — Error Handling
> Source: `ExceptionTranslator.java`

- **FR-6.1** All exception-to-HTTP-status mappings MUST route through `ExceptionTranslator.java`.
- **FR-6.2** No delegate implementation (`PetApiDelegateImpl`, `StoreApiDelegateImpl`, `UserApiDelegateImpl`) MAY contain inline `try/catch` blocks that produce HTTP response bodies directly.
- **FR-6.3** Validation errors MUST map to `400 Bad Request`; not-found conditions MUST map to `404 Not Found`; unsupported method signatures MUST map to `405 Method Not Allowed`.

### FR-7 — Date/Time Formatting
> Source: `RFC3339DateFormat.java`

- **FR-7.1** All `date-time` fields in API responses (`Order.shipDate`, `X-Expires-After` login header) MUST be serialized using `RFC3339DateFormat.java`.
- **FR-7.2** No other date formatter or inline `SimpleDateFormat` MAY be introduced.

### FR-8 — In-Memory Storage
> Source: `HashMapRepository.java`, `PetRepository.java`, `OrderRepository.java`, `UserRepository.java`

- **FR-8.1** All data is stored in JVM heap memory. No data survives application restart. This is the **intentional baseline** for the current implementation.
- **FR-8.2** `PetRepository.java` MUST support filter-by-status and filter-by-tags operations in addition to basic CRUD.
- **FR-8.3** Any future persistent storage MUST be introduced as a new implementation behind the existing repository interface — `HashMapRepository.java` MUST NOT be modified.
